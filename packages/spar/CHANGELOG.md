# Changelog

## 0.3.1

### brief の「Left unfinished last sortie」が本当に前回の分だけになった

`brief()` は台帳全体から `severity: stop` の claim を拾って末尾 5 件を出していた。
「前回の sortie」と言いながら、実際は **これまでの全拒否**の直近 5 件で、翌朝直した契約も
1 週間後まで「未完」として毎セッション冒頭に戻ってきていた。同じ件名の再試行も件数分並んだ。

読む範囲を **最後に claim を出した sortie** に絞り、件名ごとに **その後の claim が通っていれば外す**。
同じ件名は 1 行にまとめる。捨てた案（discard）の扱いは変えていない。

## 0.3.0

### `.spar` の場所を「シェルの現在地」ではなく「セッションの起点」から決めるようになった

全部品は cwd から `.spar/` を引くが、既定の cwd がプロセス自身のものだった。Claude Code の hook では
それはシェルの現在地で、Bash の中で一度 `cd` すると以後の hook は全部そこで動く。
2026-09-02 の実測で、ホームで始めた 1 セッションの redline が `reflint-vscode/.spar` で 21、
`orogami/.spar` で 3、`~/.spar` で 8 と、同じ飛行が 3 つの台帳に割れていた（9 リポに頼んでいない
`.spar/` が生えた）。

Claude Code が hook に渡す `CLAUDE_PROJECT_DIR`（起動したディレクトリ）を既定にした（`root()`）。
`SPAR_HOME` は引き続きどちらより優先。0.2.1 の melee の件も同じ根で、これで塞がる。

## 0.2.1

### `spar melee` が「どのソーティに入ったか」を言うようになった

melee は**リミッターを黙らせる操作**で、どのソーティに入るかは cwd だけで決まる
（`SPAR_HOME`、無ければ隣の `.spar`）。実測で、`dev/airframe` に cwd が残ったまま打った melee が、
稼働中セッションの `C:\Users\atlan\.spar` ではなく `dev\airframe\.spar` に入っていた。

このとき何も表示されないので、**意図したソーティに入れていないことに気づけない**。
enter と leave の両方で、操作した `.spar` のパスを1行出すようにした。

### 出撃していないソーティには入れない

さらに悪い形がその下にあった。`sortie()` は sortie.json が無いと**空の値**（`id: null`）を返し、
それが**そのまま commit できていた**。つまり何も起動していないディレクトリで melee を打つと、
まだ見張られている本物のセッションの隣に**幽霊の swing** が書かれる。しかも両者を区別する
手掛かりは何も出ない。

`id` が無いソーティは `no sortie here to commit — <path> has none launched` で断るようにした。

### README に「`spar` は airframe を link しても通らない」と書いた

`@hyuga/airframe` をグローバルに link しても `spar` はパスに乗らない（別パッケージ・別 bin）。
README が `spar melee …` を「打てる」前提で書いていたのに、そこが書いていなかった。

## 0.2.0

### `@hyuga/spar/cli` — 部品の CLI の縁を、1箇所にまとめた

`runDirectly` / `readStdin` / `emit` は spar・redline・carbon・airframe・habit に private な
コピーとして5本・3本・4本置かれていた。中身は同じで、habit だけ波括弧の位置が違った。

同じ判断のコピーは必ずずれる。しかもこの3つがずれる場所は誰も見ていない。とりわけ
`runDirectly` は **`main()` を走らせるかどうかを決める1行**で、微妙に壊れたコピーは
「インストールされているのに何もしない部品」を作る——症状の無い壊れ方だ。1本直しても、直るのは1本。

置き場所を骨組にしたのは、これを必要とする部品がすでに骨組に依存しているから。
「各部品は単体で立つ」という重複の根拠は、この4本については成り立っていなかった。
`runDirectly` は呼び出し側の `import.meta.url` を受け取る——自分では読めない唯一のもの。

habit は対象外。依存を1つも宣言していないという性質のほうが、関数3つの重複より価値がある。

### CLI を実際に起動するテストを12本

これまでのテストは全部「関数を import して呼ぶ」形で、`main()` は一度も走っていなかった。
カバレッジがそれを 412-490——コマンド表の全域——として出した。このリポジトリでは仮定の話ではない。
CLI が何もせず exit 0 する状態で公開された部品がすでに2つあり、どちらも「bin を実際に叩いて」
見つかっている。

`brief` が台帳から読み戻す行を引用することも、ここで固定した。台帳は誰でも追記できるファイルで、
brief は次のセッションに渡される。独立した行として抜け出せる文字列は、再起動を生き延びる指示だ。

## 0.1.0

最初の公開。

エージェントを見張る道具は、1本ごとに自分のCLI・自分の設定・自分の報告の形・自分の終了コードを
持っている。4本目を入れる手間が3本目と変わらないのは、**それらを束ねるものが無い**から。

spar（継手）はその束ねる側だけを引き受ける。決めているのは4つ——形態（収束するか発散するか）・
位相（brief / pre / claim / post）・所見1件の形・追記専用の台帳（`.spar/ledger.jsonl`）。
何を撥ねるかは一切決めない。それは部品の仕事で、骨組が口を出すと部品が差し替えられなくなる。

`.spar/` は作られた時点で `.gitignore`（`*`）を持つ。台帳と、cruise 中に carbon が控えた
**まだ git に入っていない下書き**が入る場所なので、`git add -A` 一発で他人のリポジトリの
履歴に混ざる。「各自 .gitignore に足してください」と README に書く類のものではない。
