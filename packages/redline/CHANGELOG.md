# Changelog

## 0.6.1

### 限界 3 を毎回越えていたのは、課金の半分以上が読み違いだったから

実機の履歴2週間分（Bash / PowerShell 6,201 回）を 0.6.0 に通し直すと、課金は 89 回・245 点。
その過半は料金表が値付けしているものではなかった:

- **一時ディレクトリの掃除が irreversible +3。** `S="$TEMP/.../scratchpad"; rm -rf "$S/asar"` は
  `$S` の行き先を読んでいなかった。
- **本番を読んだだけで production +2。** `node -e "...readFileSync('~/.claude/settings.json')..."`
  は、パスが行に書いてあるというだけで書き込み扱いだった。
- **文字列が命令扱い。** `npm publish` という語を含む契約を `node -e` で追記すると publish だった。

限界そのもの（3）は変えていない。点が正しければ 3 で足りる。直したのは読み方の側:

- コマンドを前から順に読み、同じ行で代入された変数と環境変数を展開する。読めない代入
  （`S=$(pwd)`、`for`、PowerShell の文字列以外）は展開しない。`$` が残ったパスは
  「どこでもない」扱いで、従来どおり課金する。
- 削除の対象が**全部**一時ディレクトリの中なら irreversible を課金しない。一時ディレクトリ
  そのもの・その直下の `*`・読めない変数・`cd` の無い相対パスは課金する。
- production は書き込みにだけ課金する。代入と `cd` 単体は書き込みではない。表示するだけの
  コマンドは本番へのリダイレクトにだけ課金する。`cd` 先が本番なら、そこで走らせたものに課金する。
- `node -e` / `python -c` のコードは、読める範囲（標準の fs / path 系モジュールと JSON だけ、
  子プロセス・eval なし）なら文字列をデータとして扱う。相対 `require` や `child_process` を含めば
  従来どおり語で課金する。
- `2>&1` と `&>` の `&` で区切っていたのを直した（`1` という単独の命令ができていた）。
- `package.json` を **Read / Grep しただけ**で dependency +1 だったのを、書き込みツールだけに
  絞った（pre フックは全ツールに掛かっている）。
- `sed -n 47,58p`（行範囲を印字するだけで `-i` の無い形）と `node --check`（前に `-r` などが
  無い形）を読み取りに入れた。`sed` はスクリプトに `e`（実行）や `w`（書き込み）を書けるので、
  それ以外の形は従来どおり中身で課金する。

同じ履歴を通し直した結果は 61 回・156 点。消えた 28 回は上の読み違いで、残った irreversible と
outward は作業ツリーや AppData の削除、実際の push / publish / release だった。

一方で、変数が読めるようになったぶん**新しく課金される**呼び出しもある。`$USERPROFILE` 経由で
OneDrive へ heredoc を書く、`cd "$USERPROFILE/OneDrive/..." && node --test` などで、パスを直書き
していれば 0.6.0 でも課金されていたもの。`find` や `schtasks` のように読むだけかどうかを
見分けられないコマンドは、本番のパスや本番の `cd` 先で走れば従来どおり課金する。

## 0.6.0

### `REDLINE_PRODUCTION` が設定ファイルと合算されるようになった

これまでは設定ファイルが 1 つでも見つかると環境変数は無視されていた。ホームに
`~/.redline.json` を置いた途端、環境変数で指定した本番パスが黙って消える（この
パッケージ自身のテストが 7 件、その理由で落ちていた）。方針は「合算は増やす方向にしか
間違えない」なので、環境変数もファイルと同じく合算する。テストはホームを一時ディレクトリに
向けて走るようにした。

### 既定の cwd が spar の `root()`（`CLAUDE_PROJECT_DIR`、無ければ cwd）になった

シェルが `cd` した先の `.spar` を読んで、同じ出撃の点数が台帳 3 つに割れていた。経緯は spar の CHANGELOG。

## 0.5.1

### 「melee に入れ」を、いちばん必要な場所で言っていなかった

実測でこう出た——本番ツリーへページを書くと +2、それをアップロードするとさらに +2。
**仕事を最後までやる実行は、最後の一手で必ず限界を越える。** そして越えた先の tier では、
その抜け道（melee）の案内が**出なくなっていた**。案内は warn の1行にしか付いていなかった。

越えた先で言っていたのは「限界を越えたと声に出してから進め」で、これは**うっかり1回踏んだ人**
への助言。**最初からその値段だと決まっていた一続きの作業**への助言ではない。無人時に至っては
何も言わずにコールを deny していた。

バッチは同じ形の掛け算になる。10社なら20点で、**2社目以降は全部 stop**。0.3.0 で
「点数を増やさないコールは止めない」と直した飽和に、正当な production 課金という別の入口から
戻ってくる。

案内を stop と halt にも出すようにした。halt では言い方を変えてある——**それが最初から
その値段の作業（バッチ・複数の公開）なら、コール単位で押し問答する話ではなく、走り出す前に
宣言する話**で、宣言する場所は melee。README に「最初からその値段だと決まっていた実行」の
節を足した。

検討して採らなかった案:

- **同じ production パターンの2回目以降を減点しない** — 「publish の半分」は無い。
  1社目が課金されたからといって10社目のページが無料になる理由が無い。
- **ソーティの長さに対して閾値を相対化する** — エージェントがやった量に応じて限界が伸びるのは
  限界ではない。暴走が一番得をする。

## 0.5.0

### シェルコマンドも「触るツリー」に設定を訊く

0.4.0 は書き込まれるファイルに探索を1本与え、シェルには与えなかった——文字列からパスを
取るのは推測で、外すと外した先のファイルを読むことになる、という理由で。実測がそれをひっくり
返した。**このPCで何かを公開する最後の一手はシェル**（work_log 実査で WinSCP が20件）で、
**その一手だけが「設定をどこに置いたか」で課金が変わる**構図になっていた。

| | 0.4.0 |
|---|---|
| クライアントツリーへファイルを置く（Write/Edit） | `production +2` |
| そのツリーを本番サーバーへ上げる（WinSCP・シェル） | **0点**（home に設定が無い場合） |

反論が成り立つのは「余計な読み取りでリミッターが**静かになる**場合」だけで、それは起きない。
設定は**和を取る**ので、この経路で見つかったものは production を**増やす方向にしか効かない**。
外れた推測は `existsSync` を数回無駄にするだけで、数字は1つも動かない。

1コールあたり**4パスまで**（実際の形は「元」と「先」の2つ）。読み取り専用のセグメントは
`acts()` が先に落としているので、`grep /var/www -r` は読んでいるツリーについて訊かれない。

これで会社PCの「設定を home と X: の2箇所に置いて手で同期する」運用は不要になるはず
（要検証：シェル経路が X: 側1本で拾えるか）。

## 0.4.0

0.3.0 を会社PCで1日回した実測から出た3つ。うち2つは 0.3.0 自身が持ち込んだ・直しきれなかった穴。

### 設定は「書き込む先のツリー」にも訊く（＋見つかったものは足し合わせる）

0.3.0 は cwd から上へ辿る形にした。前提が違っていた——フックの cwd は**セッションを起動した
場所**であって、作業のある場所ではない。home で起動したセッションが、cwd を1度も変えないまま
1日中ネットワーク共有のクライアントツリーへ書く。**共有の頂点に置いた設定には永遠に届かない。**

報告してきた機体は、同じ設定を2箇所（書く場所と起動した場所）に置いて手で同期する運用に
なっていた。それが回避策であって、直すべきはこちら側。

書き込み対象のファイルにも探索を1本持たせた。「どのパスが本番か」は `.gitignore` と同じく
**ファイルが住んでいるツリーの性質**で、知っているのはそのツリー。

見つかった設定は**順位付けせず和を取る**。順位付けにすると、書き込み先のディレクトリに置いた
設定がセッション側のリストを**短くできる**——監視される側が監視を静かにできてしまう。
和なら本番扱いが増える方向にしか外れない。リミッターが間違ってよいのはその向きだけ。

シェルコマンドには専用の探索を与えていない。パスを文字列から推測することになり、
推測を外すと「外した先のファイルを読む」ことになるため。

### 「1つも名前を挙げなかった」を記録する

0.3.0 の CHANGELOG は「finding は今までどおり台帳に残る」と書いたが、**最も残ってほしい場面で
残っていなかった**。プロンプトにファイル名が1つも無いと brief が1行も書かれず、`scope()` が
`null` を返し、`null` は「プロンプトフックが入っていない」と読まれて判定ごと飛ばされる。

スキル実行はまさにその形のプロンプト。`/karte <社名>` はタスクを名指しし、ファイル名はスキルが
知っている。実測では、頼まれていないファイルを4つ書いた実行が、台帳に**5つ目についての1行**しか
残さなかった。

brief は空でも書くようにした。空リストは字義どおり「1つも挙げなかった」＝全部エージェントの
発案、という意味になる。無料のまま・無言のまま・記録には残る。

### ヒアドキュメントの開始マーカーが行末でなくても剥がす

`git commit -F - <<'MSG' && git log --oneline -1` は普通に書く形で、これを剥がせていなかった
（マーカーの直後に改行を要求していた）。本文が全部コマンドとして読まれるので、**このブランチの
コミット自身がコミットメッセージ中の語句で3点ずつ課金されていた。**

本文が次の行から始まるのはどちらでも同じ。マーカーと同じ行の残りは本物のコマンドなので、
本文と一緒に飲み込まず**書き戻す**。

## 0.3.0

会社PCで1日回した実測から出た3つの修正。挙動が変わるので minor を上げた。
その日の台帳は、課金22件のうち19件が `unnamed`、同じスキルの3連続実行がそれぞれ
41秒 / 63秒 / 40秒で stop に飽和、というもの。

### `unnamed` を記録専用にした（+1 → +0）

「人がプロンプトで名前を出していないファイル」への課金は、19/22 が**スキルが仕様どおりに
書いた定型ファイル**だった。スキルは「人がタスクを言い、ファイル名はスキルが知っている」
から成立するので、この判定はそもそも**通常運転と暴走を区別できない**——区別が唯一の目的
だったのに。区別できない判定が課金の86%を占めれば、数字全体がノイズとして読まれる。
引用を課金対象から外したときと同じ理由。

finding は今までどおり台帳に残る。「頼まれていない何を書いたか」は後から読めば分かる。
点数が動かなくなっただけ。

### 点数を増やさないコールは止めない

`score()` がソーティを合算して下がらないのは**この道具の主張そのもの**なので変えない。
間違っていたのは、コール1件の severity をその累計だけで決めていたこと。おかげでソーティ
最初の不可逆コマンド1回で、以後の全コールが stop になり、無人時は全部 deny になった。

実測：スケジュール実行が開始40秒で一時ファイルを1つ消し、残りの時間ずっと scratch
ディレクトリへの書き込みを拒否され続けた。**人に引き継ぐことすらできない。**

累計を1点も増やさないコールは `note` で黙るようにした。finding は累計を持ったままなので
読みは変わらない。割り込みを、実際に露出を買っているコールの側に寄せた。

### `.redline.json` を上のディレクトリと home からも探す

探索が cwd 直下だけだった。エージェントの cwd は**作業がある場所**——ネットワーク共有の
奥のクライアントフォルダ、モノレポの中のパッケージ——であって、「どのパスが本番か」を
書き留める場所ではない。しかも**見つからないことは無言**で、道具は数字を出し続ける。

実測：本番Webサーバーに上がるクライアント向けHTMLが、全部 `production +2` ではなく
`unnamed +1` として課金されていた。その日いちばん外向きの書き込みが伝票上いちばん安く、
捨てるための一時ファイルの削除が3倍高かった。

cwd → 上のディレクトリ全部 → home の順に探す。近い方が勝ち、壊れたJSONは探索を止めない。

## 0.2.0

### `@hyuga/spar@^0.2.0` を要求するようになった

`runDirectly` と `readStdin` を自前のコピーから `@hyuga/spar/cli` に移した。この副経路は
spar 0.2.0 で入ったもので、公開済みの 0.1.0 には無い——依存の下限を上げずに公開すると、
インストールした人の環境で `ERR_PACKAGE_PATH_NOT_EXPORTED` になる。しかもフックの中なので、
**エラーですらなく「黙って何もしない limiter」**になる。

### CLI を実際に起動するテストを14本

`check()` は十分覆われていて、`main()`——stdin を読み、封筒を選び、黙るかどうかを決める部分——は
一度も走っていなかった。ここで固定したのは主に2つ:

- 席に人が座っているときは `additionalContext`、無人のときだけ `permissionDecision: deny`。
  **上書きできる助言と、機械が自分を止めることは別物**で、その2つはフィールド1つ分しか離れていない。
- `{` / `null` / `[]` / 型の違うペイロードを渡しても、必ず exit 0 で無言。
  セッションを壊す limiter は、limiter が無いより悪い。

### スコープが前の出撃のものだった

「利用者が名前を出したファイル」の一覧を台帳から拾うとき、出撃で絞っていなかった。台帳は

## 0.1.0

最初の公開。

1回ごとの許可確認は、10回目には意味を失う。押している側は「さっきと同じやつ」としか思わないので、
**危険なのは1回の呼び出しではなく、1セッションで積み上がった量**の方だという事実が見えない。

redline（際）は呼び出しではなく出撃を数える。本番への書き込み・不可逆な操作・依存の追加を種類ごとに
加算し、上限に達したら告げる。人が座っているセッションでは**止めずに具申する**——飛ばしているのは
パイロットで、際を越えるかどうかはその人の判断だから。止めるのは `AIRFRAME_AUTONOMY` が立っている
とき、つまり誰も座っていないときだけ。

### 引用は課金しない

このリミッタは、他人に何かを払わせる前に自分の信用を落とした。`npm publish` という文字列を
**検索しただけ**のセッションが、上限3に対して20点まで上がった。中身は README の grep と
workflow ファイルの閲覧で、課金された全部が引用だった。

原因は、コマンドを1つの文字列として正規表現に当てていたこと。コマンドは1つの動作ではない
——`grep "npm publish" README.md && npm publish` はその語を2回含み、publish は1回しかしない。
文字列全体に当てれば両方に課金され、どちらが本物だったかは後から誰にも分からない。

コマンドを実際に走るものへ切り分けてから当てるようにした。区切りはクォートの外の `;` `|`
`&&` `||` と改行で、**印字するだけの動詞**（grep / rg / cat / head / echo / ls / Select-String 等）
で始まる区間は落とす。ヒアドキュメントの本体も落とす——書かれているファイルの中身であって、
実行される行ではないから。`find` `sed` `awk` `xargs` は落とさない。いずれも引数がそれ自体
コマンドなので、その引数は「ただの文字列」ではない。

本番パスの判定も同じ扱いにした。`grep -r X:/01-client/ notes/` は本番の名前を口にするだけで、
本番に届いてはいない。

数字が雑音で埋まると雑音として読まれ、そのとき止めるべき1件が、止めなくてよかった20件と
同じ顔で流れていく。
